<section class="case-study-intro-callout" aria-labelledby="document-intelligence-intro-title">
  <h2 class="case-study-intro-callout__title" id="document-intelligence-intro-title">TURNING PROBABILISTIC EXTRACTION INTO GOVERNED ACCOUNTING DATA</h2>
  <p class="case-study-intro-callout__body">In accounting automation, Artificial Intelligence models can extract vendor identifiers or tax amounts that appear syntactically correct, but are mathematically or fiscally incorrect. The engineering challenge is not simply to extract text, but to design an architecture that strictly controls when an AI "guess" can become official accounting data suitable for an ERP.</p>
</section>

## SOLVES THIS PROBLEM THROUGH AN ABSOLUTE SEPRATION<br />BETWEEN UNCERTAINTY (AI) AND AUTHORITY (BASE SYSTEM)

The platform operates under a strict design rule: a model's output is always a proposal, never an accounting truth. To guarantee this, the system divides its topology into two major blocks:

      - Python and Temporal Workers:
            They are responsible for orchestration,
             OCR routing, calls to LLMs, and normalization.
            They propose candidate data.

      - Central API in Go and PostgreSQL (Authority):
            Retains exclusive control over the document lifecycle.
            It is the sole entity with write permissions
            to the tenant databases and is responsible
            for approving or rejecting state transitions.

<Disclosure title="GOVERNANCE AND MULTI-TENANT SECURITY">

## GOVERNANCE AND MULTI-TENANT SECURITY

The design prioritizes transactional security and data isolation:

      - Isolation by Design:<br /> Strict data separation using PostgreSQL schemas and S3 storage prefixes.

      - Ephemeral Credentials:<br />Workers operate without direct database access. They use short-lived tokens limited to a single tenant, a single document, and a single execution.

      - Clean History:<br />Sensitive data such as PII, tax identification numbers (TIN), or monetary amounts never enter Temporal event payloads, ensuring a secure and compliant audit trail. A model can return a plausible supplier identifier, invoice date, tax amount, or total that is syntactically correct and still wrong. The engineering challenge is therefore not limited to extracting fields. The platform must control when uncertain evidence can become durable canonical data and when that data may leave the system.

</Disclosure>

The raw data and spatial coordinates detected by the OCR and Vision engine.

### Canonical Candidates

### Validated Canonical Data

Values that have passed the validator's rigorous mathematical and logical rules.

<Disclosure title="Code evidence: workers/temporal-python/activities/validator.py">

```python
for taxable_key, tax_key, total_key in CANONICAL_AMOUNT_TOTAL_GROUPS:
    if {taxable_key, tax_key, total_key}.issubset(canonical_invoice_data):
        if not validate_decimal_string_amount_total(
            canonical_invoice_data[taxable_key],
            canonical_invoice_data[tax_key],
            canonical_invoice_data[total_key],
        ):
            blocking_reasons.append(
                f"{taxable_key}_plus_{tax_key}_must_match_{total_key}"

```

This rule verifies that:

**Taxable Amount + Tax Amount = Total Amount**

Test evidence: `workers/temporal-python/tests/test_validation_rules.py` verifies exact decimal reconciliation, total mismatches, and Portuguese NIF validation.

Passing these checks produces a successful validation outcome. It does not automatically grant the same authority as a human reviewer decision.

</Disclosure>

### Reviewer Decisions

If the validator detects an anomaly, a human intervenes. Human decision holds absolute authority over the automation.

<Disclosure title="Code evidence: services/api/internal/store/review_store.go">

```sql
UPDATE field_candidates
SET candidate_value = $1,
    produced_by = 'reviewer',
    validation_status = 'valid',
    updated_at = now()
WHERE document_id = $2
  AND canonical_field_name = $3
```

The decision is recorded through these events:

- `review.corrections_recorded`
- `review.validation_outcome_recorded`

The events are persisted in:

- `document_history`
- `control_plane.audit_log`

Reviewer-owned candidates are protected from subsequent automated updates.

</Disclosure>

> *Human reviewer decisions have protected transactional authority over automated candidates and remain fully auditable.*

</Disclosure>

## The Document Lifecycle

### Intake

The Go API accepts bounded document uploads, resolves the tenant context before processing the file, stores the document under a tenant-scoped key, and atomically creates the document and its intake audit event. PostgreSQL initializes the document in the `intake_registered` state and records its reception timestamp.

<Disclosure title="Code evidence: db/migrations/tenant_template/0001_documents.up.sql">

```sql
lifecycle_state document_lifecycle_state
    NOT NULL DEFAULT 'intake_registered',

created_at timestamptz
    NOT NULL DEFAULT now(),

updated_at timestamptz
    NOT NULL DEFAULT now()
```

**Supporting evidence**

- Validates the tenant context and limits upload size.
- Verifies the user token and resolves tenant membership.
- Creates the document and the `document.intake_registered` audit event in one transaction.
- Proves that `received_at` is derived from `documents.created_at`.

</Disclosure>

> **Accuracy note:** *Secure tenant resolution is guaranteed in production Clerk mode. The alternative pilot-header mode must remain behind a trusted boundary.*

### Orchestration and Extraction

A Python Temporal workflow classifies the PDF processing shape as digital, scanned, or complex and selects the appropriate text or vision route. It then runs header, line-item, and totals extraction concurrently through specialized AI inference activities.

<Disclosure title="Code evidence: workers/temporal-python/workflows/document_processing_workflow.py">

```python
header_ref, lines_ref, totals_ref = await asyncio.gather(
    workflow.execute_activity(header_specialist, ...),
    workflow.execute_activity(lines_specialist, ...),
    workflow.execute_activity(totals_specialist, ...),
)
```

**Supporting evidence**

- `activities/document_processing.py` classifies documents as digital, scanned, or complex.
- `activities/structure_fields.py` defines separate header, line-item, and totals extraction activities.
- The specialists submit text or page images through the AI inference gateway.
- `tests/test_specialist_branch_retry.py` proves that one failed branch can retry without rerunning the other specialists.

</Disclosure>

> **Accuracy note:** *PDF processing shape, fiscal document type, and business category are three separate classifications. The inference gateway can use Bedrock or vLLM depending on deployment configuration.*

### Deterministic Validation

Canonical invoice data is validated using exact base-10 decimal arithmetic. The system verifies subtotal-plus-tax against the total, validates Portuguese NIF checksums, restricts accepted VAT rates, and reconciles multi-rate VAT bands against document totals.

<Disclosure title="Code evidence: workers/temporal-python/activities/validator.py">

```python
def validate_amount_total(
    taxable_amount: Any,
    tax_amount: Any,
    total_amount: Any,
) -> bool:
    taxable = to_decimal(taxable_amount)
    tax = to_decimal(tax_amount)
    total = to_decimal(total_amount)

    if taxable is None or tax is None or total is None:
        return False

    return taxable + tax == total
```

This verifies `Taxable Amount + Tax Amount = Total Amount`.

- Exact decimal totals pass validation.
- A one-cent mismatch fails validation.
- Portuguese NIF checksums are verified.
- VAT rates are restricted to 0, 6, 13, and 23.
- Multi-rate VAT bands must reconcile with document totals.

</Disclosure>

> **Accuracy note:** *The validator intentionally uses exact decimal equality and never binary floating-point arithmetic for fiscal amounts.*

### Human Review and Approval

Every processed document transitions to `ready_for_review`. Any exact arithmetic mismatch, including a one-cent difference, creates a blocking validation reason. The Go API prevents approval until validation succeeds and all mandatory fields are resolved. Reviewer corrections are marked as reviewer-owned, remain auditable, and cannot be silently overwritten by subsequent automated extraction.

<Disclosure title="Code evidence: Approval-blocking evidence">

`services/api/internal/review/review_service.go`

```go
        ctx,

}
```

</Disclosure>

### Approved Export Delivery

Before a document can be exported, the platform verifies its lifecycle approval, review approval, validation result, and canonical-data completeness. Approved documents can currently be delivered through the direct API as canonical JSON or a SAF-T-compatible pilot envelope.

<Disclosure title="Code evidence: services/api/internal/export/export_service.go">

```go
if !lifecycleAllowsExport(candidate.LifecycleState) {
    reasons = append(reasons, "approval_required")
}

if candidate.ReviewStatus != "approved" &&
    candidate.ReviewStatus != "not_required" {
    reasons = append(reasons, "review_not_approved")
}

if !candidate.ValidationPassed {
    reasons = append(reasons, "validation_failed")
}

if !candidate.ExportComplete {
    reasons = append(
        reasons,
        "export_requirements_incomplete",
    )
}
```

**Supporting evidence**

- `export_service_test.go` proves that blocked documents never reach the export builder.
- `exportprofile/exportprofile.go` defines profile metadata for CSV, XML, and JSON.
- `store/db_harness_test.go` verifies that profile delivery applies the same approval and validation gates.

</Disclosure>

**Important limitation**

The current direct export service fully exposes:

- `canonical_json`
- `saft_pt_compatible`

CSV rendering exists in the codebase but is currently rejected by the direct service allowlist. XML is supported as profile configuration, but no operational XML renderer or HTTP delivery route is currently wired.

> **Production wording:** *The platform currently delivers approved canonical JSON and a SAF-T-compatible pilot envelope, while the profile architecture establishes the foundation for future CSV, XML, and JSON ERP integrations.*

</Disclosure>

<Disclosure title="System Limits">

3. Límites del sistema
- Límite público: únicamente el portal Next.js y el API Go están expuestos a usuarios.
- Límite interno: FastAPI, workers, OCR y servicios de inferencia permanecen dentro de la red privada.
- Autoridad de datos: solamente el API Go escribe directamente en PostgreSQL y controla los estados del documento.
- Aislamiento por tenant: PostgreSQL separa los datos por esquemas y S3 mediante prefijos de objetos.
- Orquestación: Temporal coordina procesos y reintentos, pero no es la fuente de verdad de los documentos.
- Proveedores externos: Clerk gestiona identidad y Bedrock proporciona inferencia administrada.
- Componentes opcionales: vLLM/Qwen y el pipeline PP-DocLayoutV3/GLM-OCR requieren activación explícita.
- Exportación: el sistema genera y registra archivos para ERP

</Disclosure>

5% overall field accuracy, 90% per-field accuracy, no more than 2% nulls, and zero mathematical errors. It evaluates field values, source evidence, review routing, export readiness, validation failures, and total reconciliation.

These values are configured thresholds. They are not proof that the platform has achieved those results in production.


## Transferable lessons

1. **Keep probabilistic processing away from authoritative writes.** Models and orchestration should propose evidence. A smaller trusted boundary should own state changes.
2. **Canonicalize before validating.** Deterministic rules need stable, versioned field definitions.
3. **Turn every refusal into a reason.** Explicit blocking reasons make uncertainty reviewable, testable, and auditable.
4. **Make human authority durable.** Reviewer decisions must survive automation reruns.
5. **Separate verification from business outcomes.** Passing tests demonstrate contract evidence for a revision, not production success.
